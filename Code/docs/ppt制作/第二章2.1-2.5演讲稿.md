> 汇报口径（演示版）：本章使用 `flow_validation` 演示链路，已经可以展示四路 JEV/Laya-JEV 分流、full_loop 五类 Agent 协作、人工动作和报告归档。视觉精度、专家路由训练、视频-过程融合和在线 RSI 仍属于论文级待优化内容。讲解时区分“演示验证”“现有工程模块”和“论文级待优化”，不把结构验证素材说成模型效果。

## 2.1 项目数据与证据源

**演讲稿**

这一页先回答一个问题：系统做一次火眼诊断时，依据从哪里来？我们目前把证据分成四类。第一类是火眼短视频或图片，用来观察火眼区域的外观和变化；第二类是过程数据，目前有 14 个变量，可以从历史窗口中提取工况趋势；第三类是工艺知识，包括过热度定义、工艺规则和现场检查事项；第四类是经过人工审核的历史案例，记录结论、证据和复核意见。

这里需要特别说明，现有过程数据没有与火眼视频逐条对应的时间戳。因此，它暂时不能作为视频的同步标签。我们把视频和过程数据作为两类独立证据，分别分析，再通过任务协议交给相应模块使用。这样既能利用过程数据提供工况背景，也不会声称数据之间存在尚未验证的对应关系。下一页我会说明这些不同来源的信息如何组织成统一任务。

**本页要让听众记住**：系统有视觉、过程、知识和案例四类证据，视频与过程数据目前分别产生。

**转场句**：有了不同来源的证据，接下来需要定义统一的任务格式，让各个模块能准确交接信息。

## 2.2 任务数据组织与标注协议

**演讲稿**

这一页展示系统内部的“任务交接单”。左边是一次巡检任务可能带来的输入，例如媒体文件、抽取帧和可选的过程数据窗口。中间的 `InspectionTask` 负责记录任务输入和运行追踪信息；右边是 Agent 返回的结构化结果，例如视觉证据、过程状态摘要、证据引用和复核决定。图里的 `media_uri`、`frame_ids`、`roi`、`process_window` 是面向目标版本的任务结构示意；当前代码中的 `InspectionTask` 核心字段是 `input_path`、`run_id`、`tenant_id`、`session_id`、`operator_id` 和 `input_mode`。

下方把标注分成视觉、过程和诊断三类：视觉侧描述 ROI、类别和图像质量；过程侧描述趋势、波动和缺失情况；诊断侧记录风险、依据、现场检查项和人工动作。这些字段定义了数据如何交接，并不代表所有输入已经时间对齐。统一协议的作用是让不同 Agent 交接时知道“输入是什么、结果是什么、证据来自哪里”。如果展示代码，可以把 `InspectionTask` 的字段定义放在图旁边，帮助听众看到任务对象如何承载输入和追踪信息。下一页再看这些角色如何在整体架构中协同。

**本页要让听众记住**：协议统一的是任务和结果的表达方式，不会自动建立视频与过程数据的时间对应关系。

**转场句**：任务和结果有了共同格式，系统就可以按职责安排不同 Agent 处理。

## 2.3 多智能体总体架构

**演讲稿**

这一页从整体上看系统如何工作。上方是在线主链：任务先经过质量检查和视觉取证，再结合规则或案例检索，由 JEV 判断后续需要多大诊断工作量。证据比较稳定时，进入 `simple_loop`，由轻量诊断和证据检查完成研判；遇到证据冲突、风险较高或知识不足时，进入 `full_loop`，让视觉复核、工艺知识、特殊案例和过程状态等角色并行提供证据，再由诊断聚合和证据复核模块汇总。

人工确认负责最终审核。底部的统一协议、模型网关、知识与案例库、运行审计和评测体系，为在线流程提供支撑；RSI 则读取运行记录，在离线评测和审核后提出候选改进。当前演示模式已经能够回放四路路由、full_loop 五类 Agent 和人工动作；真实模型效果与原生 checkpointer 的生产化接入仍作为后续优化项。下一页会把在线任务的状态变化单独展开。

**本页要让听众记住**：JEV 负责选择诊断路径，多 Agent 负责提供专业证据，人工负责最终确认。

**转场句**：总体架构说明了模块关系，下一页进一步说明一项任务在系统中的状态如何变化。

## 2.4 在线任务状态机

**演讲稿**

这一页讲一项巡检任务从进入系统到归档的目标状态变化。任务先检查输入和图像质量，再形成视觉证据，之后进入 JEV 路由。JEV 有四种处理方向：证据稳定时走 `simple_loop`；需要更多专业证据时走 `full_loop`；图像质量不够时请求补拍；风险较高或关键证据不足时交由人工复核。仓库中已经有独立的 LangGraph 条件路由图，能按路由结果进入相应分支。

走诊断路径的任务会经过诊断聚合和证据复核，再交给操作人员确认。人工可以确认归档、修改补充、驳回重做，或要求补拍。演示模式已经可以回放四个人工动作并写入演示审计记录；原生 LangGraph checkpointer 的网页端重启恢复仍属于论文级工程优化。讲解代码时可展示 `add_conditional_edges`，说明路由结果如何改变图的后续节点。

**本页要让听众记住**：状态机管理任务流转，JEV 决定诊断路径，人工确认完成审核闭环。

**转场句**：状态机规定了流程怎么走，最后一页再看流程中的各个角色分别承担什么职责。

## 2.5 多 Agent 角色矩阵

**演讲稿**

这一页回答两个问题：为什么要拆分多个 Agent，每个角色具体负责什么？任务接入和图像质量模块负责检查输入；视觉取证角色定位火眼并分析图像；Process State Agent 从过程变量中提取趋势和工况摘要。知识 Agent 查找工艺规则，案例 Agent 检索经过审核的历史记录。JEV 根据证据和风险选择诊断路径，诊断聚合 Agent 形成研判草案，证据复核 Agent 检查结论是否有依据，最后由人工确认和归档。

右侧的小图强调这些角色之间有串联、并行和回流关系，不是把几个模型简单排成一条队伍。这里的 Agent 指按职责划分的工作角色，可以由视觉模型、规则、检索工具或大模型实现，不要求每个角色都单独调用一个大模型。过程状态与视频视觉证据分别产生，再按任务中实际可用的信息协作。至此，数据来源、任务协议、总体架构、流程状态和角色分工就连成了一条完整的讲述线。

**本页要让听众记住**：多 Agent 是专业分工与协作机制，不等于多个大模型轮流回答。

**转场句**：明确了角色之后，下面进入多模态感知部分，先看视觉 Agent 如何从短视频中提取火眼证据。
