# 铝电解视觉-知识多智能体全局规划

> 版本：v1.2
> 目标：在现有火眼识别项目和 EduAgent 工程参考的基础上，构建一个可演示、可审计、可评测的铝电解视觉与工艺知识协同研判系统。
> 范围说明：本规划面向本地研发、验证和项目申报，不把机器人端侧部署作为当前目标。

### 0.1 路由术语与实现边界

本文固定使用以下术语，避免把参考思想、开源基座和本地业务实现混为同一个“模型”：

| 名称 | 本项目中的含义 |
|---|---|
| **JEV** | 参考的证据驱动路径选择思想，用于根据风险、证据完整性和不确定性决定诊断深度；不是本项目重新提出的通用模型名称 |
| **Laya** | 复用的开源轻量路由器基座，提供可选的预测、拟合、校准和 abstain/unbound 接口 |
| **Laya-JEV** | 在 Laya 上按 JEV 思想进行铝电解火眼领域适配后的路由器，输出 `simple_loop/full_loop/retake/human` |
| **完整系统** | `Laya-JEV + 确定性安全门控 + LangGraph 编排 + 人工审核`；Laya-JEV 只选择诊断路径，不替代视觉分类、知识检索或人工授权 |

当前实现优先保证规则门控和安全 fallback；Laya 适配、拟合和概率校准属于可选增强，未取得专家路由标注时不能声称完成监督训练或专家级准确率。

## 1. 项目目标

本项目不是把若干个 LLM 并排摆在界面上，而是把铝电解火眼巡检任务拆为专业角色，给每个角色匹配合适的算法范式和模型，再通过明确的状态、证据协议和人工复核进行协作。

预期形成以下能力：

- 输入火眼图片，或从短视频中抽取多帧窗口；进行短时视觉状态建模，不做长周期时序预测。
- 视觉分类模块使用 YOLO 多帧 ROI、空间-时序编码器和 F-GMVAE-T 专家先验融合，输出类别、风险、不确定性和动态证据。
- 工艺知识与已审核案例提供有出处的领域依据。
- 独立过程状态 Agent 建模未与视频配对的 14 维过程变量及其窗口统计特征，输出工况状态、过程事件风险和过程规则，并为 Laya-JEV 提供过程状态先验。
- 多模态模型按结构化协议形成研判草案，证据复核器检查支持关系与安全边界。
- 低质量、证据不足、模型异常或结论冲突时，系统转向补拍或人工复核。
- 每次运行都能看到模型配置、角色输入输出、证据来源、耗时、降级状态和人工决定。
- 通过冻结案例集和版本对照，衡量系统完整性、领域可用性和运行质量的变化。

系统当前输出定位为“视觉工况与风险辅助研判”，不把 C/N/H 图像分类等同于摄氏度过热度，不自动生成加料、调压等生产控制指令。缺少电解质实测温度和成分/初晶温度依据时，不输出数值过热度。

## 2. 架构原则

总体沿用 EduAgent 课件《10-02 多 Agent 能力迁移场景》的四步法：

1. **按职责拆角色**：按视觉取证、知识检索、诊断、质疑复核和人工确认划分职责。
2. **为角色选择范式**：并行评审、RAG、Human-in-the-Loop、状态机和工具调用按任务需要组合。
3. **按依赖组织协作**：独立工作并行 fan-out/fan-in；有先后依赖时使用 Pipeline；只有确有不同任务类型时才加路由。
4. **补充可复用地基**：统一模型网关、结构化状态、会话/运行标识、容错、日志、历史记录和网页可视化。

Agent 可以由传统视觉模型、确定性规则、检索器或 LLM 实现。使用多个 LLM 不是架构目标本身；每个角色应有不同输入、职责和可验收输出。

## 3. 规划起点基础与差距（历史基线）

本节记录本规划初次编制时的代码状态，保留用于说明迁移动机和技术差距；它不是当前实现状态。当前实现、验收状态和证据边界以第 13 节及 G0-G7 阶段报告为准。

| 能力 | 当前状态 | 主要差距 |
|---|---|---|
| 视觉检测与分类 | 现有 YOLO + ResNet，支持单张图片或视频代表帧 | 需要升级为多帧 ROI、空间-时序编码器和 F-GMVAE-T；ResNet 保留为基线，不作为最终主模型 |
| 过程时序数据 | 已有单槽 14 维过程变量、窗口统计特征和事件标注，但无法与视频建立样本级对应 | 先由独立 Process State Agent 做工况建模、变化点检测和过程事件风险提取，并将结果作为任务级过程先验 |
| Agent 编排 | LangGraph 固定链路：视觉 → 知识 → 诊断 → 复核 → finalize | 尚无并行 fan-out/fan-in、条件分支、可配置流程和多轮任务状态机 |
| 知识检索 | `LocalKnowledgeRetriever` 扫描 Markdown/TXT，返回 source ID 和分数 | 当前是本地词面检索；领域知识量少，尚无版本/适用范围治理、Embedding/Reranker/Milvus |
| 多模态模型 | Agent 工作流的诊断与可选 LLM 复核直接走 Ollama `/api/chat` | Agent 图还没有接入统一 OpenAI 兼容模型客户端，不能为不同角色配置模型 |
| 云端模型配置 | `Code/llm_api_client.py` 和 `Code/config/llm_api.json` 已有 OpenAI 兼容 API 配置，预设包含 Qwen 等 | 该客户端主要服务现有界面分析；当前 Agentic 工作流未复用它，因此这不等于多模型 Agent 已完成 |
| 诊断编排路由 | 当前没有独立的难度/证据路由器，默认进入固定链路 | 需要在多帧视觉初筛之后加入 Laya-JEV，在 JEV 参考思想约束下区分简单小循环、完整大循环、补拍和人工复核 |
| 结构化任务与审计 | 有 `InspectionTask`、`AgentResult`、`EvidenceRef`、`ReviewDecision` 等协议草案，JSONL 运行记录和候选案例记录 | `AgentResult/EvidenceRef` 尚未贯穿所有图节点；运行记录仍为本地文件 |
| 人工复核 | 有人工复核门控和 CLI 决策记录 | 未通过 LangGraph `interrupt/resume` 在网页中暂停、审核、恢复；CLI 决策还未与具体候选结果关联成完整审核工作台 |
| 网页可视化 | Streamlit 显示流程图、节点状态/耗时、诊断和审核 JSON | 同步运行；没有后台任务队列、流式事件 API、持久化任务历史和网页审批操作 |
| 评测与 RSI | 尚未形成冻结测试集或案例演化机制 | 需先建立单帧/多帧/F-GMVAE-T 基线和过程分支边界，再做受控的提示/知识/工作流改进 |

规划起点成熟度应表述为：**单场景、以单帧/代表帧为主的视觉证据驱动固定 LangGraph 多智能体原型，具备基础运行审计和人工门控骨架；多帧 F-GMVAE-T 与过程状态 Agent 当时属于规划升级。当前状态请以第 13 节为准。**

## 4. 多模型策略：不限定单一 Ollama 小模型

项目支持多种模型与 API 的方向是确定的：本地 Ollama 用于离线/低成本快速验证；Qwen 云端视觉 API 用于更强的视觉理解；不同尺寸的 Qwen 文本或视觉模型可以分别承担轻量路由、知识整理、复杂诊断和高风险复核。后端接口与模型 ID 应通过配置管理，避免写死在 LangGraph 节点中。

项目已有 OpenAI 兼容客户端和 Qwen provider 配置入口，后续应将其抽象成 Agent Runtime 共用的 **LLM Gateway**。每次模型调用记录 provider、model ID、角色、超时、输出 token 限制、响应状态和耗时。云端模型只接收完成本次任务所需的图像 ROI 与必要上下文，不传无关历史或内部私有推理过程。

### 4.1 角色模型档位建议

| 角色 | 首选模型类型 | 升级/回退策略 |
|---|---|---|
| 任务分流与简单摘要 | 小型文本模型或确定性规则 | 置信度低时转诊断 Agent；不将图片交给纯文本模型 |
| 图像质量与初筛 | OpenCV/传统图像指标 + YOLO 多帧 ROI | 质量门控未通过时直接请求补拍；不靠更大 LLM 掩盖模糊输入 |
| 视觉时序分类 | F-GMVAE-T：空间编码器 + Temporal Transformer/GRU + 静态/动态专家先验 | ConvNeXt-Tiny 为主模型，GRU/TCN 为小样本对照；现有 ResNet 仅作为基线 |
| 过程状态建模 | 独立时序编码器 + 变化点检测 + 模糊规则 | 未与视频可靠映射时只输出工况状态、异常分数和过程标签，不进入视频分类样本 |
| Laya-JEV 编排路由 | Laya 开源基座 + JEV 路径选择思想 + 特殊案例检索 + 确定性安全门控 | 高风险、冲突、边界质量、无可靠案例或自身异常时只允许完整大循环/人工 |
| 视觉诊断 | 能处理图片且支持所需结构化输出的 Qwen-VL/API 档位 | 本地小模型可用于快速基线；困难样本、低置信度或冲突样本可升级到更强云端视觉模型 |
| 工艺知识检索 | 词法/向量检索工具，不要求调用大模型 | 可用小型文本模型做 Query 改写或结果摘要；检索证据本身必须可追溯 |
| 案例检索 | 相似案例检索工具 | 无匹配时明确返回空结果，不让模型编造历史案例 |
| 证据复核 | 确定性校验优先；可选独立视觉语言模型复核 | 高风险/争议案例升级到更强视觉模型或人工；模型复核不能替代安全规则 |
| 报告组织 | 小型文本模型 | 只能重组已确认的结构化字段，不能补造新诊断事实 |

### 4.2 模型选择方式

- **研发默认档**：可选择本地 Ollama 小/中型视觉模型，便于离线调试和流程开发。
- **高能力档**：可配置支持视觉输入的 Qwen 云端模型，处理复杂火眼图像或模型争议样本。
- **混合档**：传统视觉检测 + 本地快模型初筛；达到预设升级条件时再调用云端强模型；复核规则独立运行。
- **全云端档**：开发/演示时允许将视觉诊断与文本角色分别绑定到不同 Qwen API 模型。
- **模型对照档**：在同一冻结案例集上切换 provider/model profile，比较输出质量、拒答行为、耗时、失败率和 Token 消耗。

具体可用模型 ID、API 版本、视觉能力、结构化输出支持、上下文长度、速率限制和价格会变化，应放在配置/模型注册表中，并在实验启动时做能力检查。文档和提示词中不要把某个短期型号名当成永久依赖。

阿里云百炼官方文档提供视觉理解 API 的 OpenAI 兼容调用方式，也提供 DashScope 原生 API；官方文档说明地域/Workspace 对应的 API Key 和 Base URL 需要匹配。模型目录会持续更新，因此实现时从官方目录选择当期可用模型，并把 `base_url`、`model`、`api_key_env` 配置化，而不是在流程代码中固定型号。[视觉理解 API](https://help.aliyun.com/zh/model-studio/vision) · [模型目录](https://help.aliyun.com/zh/model-studio/models)（查阅日期：2026-11-07）。

建议的逻辑配置形态：

```yaml
profiles:
  local_fast:
    provider: ollama
    model: ${MARS_MODEL_LOCAL_VISION}
    capabilities: [vision, json]
  qwen_vision_primary:
    provider: qwen
    model: ${MARS_MODEL_QWEN_VISION}
    capabilities: [vision, json]
  qwen_vision_escalation:
    provider: qwen
    model: ${MARS_MODEL_QWEN_VISION_STRONG}
    capabilities: [vision, json]
  qwen_text_light:
    provider: qwen

```

以上是配置设计示意，不是当前已实现配置格式。API Key 只从环境变量或本地 `.env` 读取，不写入版本库。角色可以在设置页选择 profile；每次运行需保存实际解析出的 provider/model ID，确保结果可复现。

### 4.3 JEV 思想与 Laya-JEV 任务分流器

本项目对 JEV 的定位是**参考一种证据驱动的诊断路径选择思想**，而不是声称重新提出或复现一个名为 JEV 的通用模型。工程实现以开源 **Laya** 路由器为可选基座，输入铝电解巡检任务的结构化证据，经过领域适配、概率校准和确定性安全覆盖后，形成项目内的 **Laya-JEV 路由器**。因此术语关系固定为：

```text
JEV：参考的证据价值评估/路径选择思想
Laya：实际复用的开源路由器基座
Laya-JEV：面向铝电解火眼诊断的领域适配路由器
完整系统：Laya-JEV + 安全门控 + LangGraph 编排 + 人工审核
```

为控制真实视频巡检的单次诊断时延，在昂贵的多模态诊断和多 Agent 协作之前增加 Laya-JEV。它不是 C/N/H 分类器，也不负责给火眼画面下最终结论；它只判断当前诊断任务应该运行“简单小循环”还是“完整大循环”，并可输出补拍或人工复核路径。规则优先级高于 Laya-JEV；Laya 不可用、置信度不足、abstain/unbound 或路由异常时进入安全 fallback。

JEV 只负责判断“这次任务应该走哪条诊断循环”，不负责给出最终工艺结论，不替代知识库引用、证据复核或人工确认。C/N/H、F-GMVAE-T 输出、跨帧稳定性和过程状态快照只是上游 Agent 提供给 JEV 的证据特征，不是 JEV 的预测目标。未与视频可靠对齐的历史过程数据不能直接作为 JEV 的在线输入。它接收低成本阶段已经产生的信号：

- 图像质量、目标是否存在、YOLO 多帧置信度和类别边界；
- F-GMVAE-T 的 C/N/H 概率、风险、不确定性、跨帧一致性和关键证据帧；
- 与已审核特殊案例的相似度、案例适用范围和版本；
- 必要证据是否齐全、知识检索是否有有效命中；
- 风险等级、视觉结果之间的冲突、输入是否处于训练分布之外；
- 历史人工改判、补拍和失败记录形成的难度特征；
- 只有在运行时有可靠映射时才使用的 `ProcessStateSnapshot`；未配对过程数据只进入离线知识/策略库。

建议输出固定为可审计 JSON：

```json
{
  "route": "simple_loop|full_loop|retake|human",
  "difficulty_score": 0.0,
  "novelty_score": 0.0,
  "confidence": 0.0,
  "risk_level": "low|medium|high",
  "similar_case_ids": [],
  "evidence_gaps": [],
  "reasons": [],
  "process_context_used": false,
  "alignment_quality": "unknown",
  "model_profile": "laya_jev_router_v1",
  "gate_version": "laya-jev-policy-0.1"
}
```

分流策略必须保守：高风险、置信度不足、图像质量处于边界、证据冲突、没有可靠相似案例或 JEV 自身异常时，不得进入简单小循环，直接进入完整大循环、补拍或人工复核。只有“质量合格 + 低风险 + 证据充分 + 相似案例满足适用条件 + JEV 置信度达到阈值”的任务才允许进入简单小循环。阈值应在冻结评测集上校准，而不是凭经验写死。

对于视频输入，先按固定策略抽取短视频多帧窗口，不把整段视频直接交给每个 Agent。视觉分类模块使用 YOLO 逐帧 ROI、空间编码器和 Temporal Transformer/GRU，F-GMVAE-T 输出跨帧状态、风险和不确定性；帧间结论不一致、目标变化明显或无法形成稳定证据时，自动升级到完整流程或人工复核。这里的时序建模只描述短时视觉状态，不代表长周期预测，也不从图像推断未提供的温度时间序列。

在通过率为 `p_fast` 时，可用下面的量化关系评估分流收益：

```text
平均时延 ≈ T_jev + p_small × T_small + (1 - p_small) × T_full
平均 Token ≈ C_jev + p_small × C_small + (1 - p_small) × C_full
```

分流带来的效率提升只能在危险样本漏放率、复杂样本完整流程召回率和人工改判率不恶化的前提下成立。

### 4.4 多帧视觉分类与非配对过程数据

论文中的 F-GMVAE 提供了静态、动态和过程特征通过模糊标签与高斯混合先验进行多源对齐的思路。本项目将其扩展为 **F-GMVAE-T**：

```text
短视频多帧
  → YOLO 逐帧 ROI 检测、跟踪和对齐
  → ConvNeXt-Tiny/轻量 ViT 空间编码器
  → Temporal Transformer（GRU/TCN 作为小样本对照）
  → 视觉时序嵌入

静态/动态专家特征
  → 模糊 IF-THEN 标签
  → 条件高斯混合先验
  → KL 对齐 + 对比对齐 + 分类
  → C/N/H、风险、不确定性、动态证据和关键帧
```

静态特征包括亮度、对比度、饱和度和纹理；动态特征包括灰度/结壳变化速率、角点速度、ROI 结构变化和光流统计。现有 ResNet 只作为基线，不作为最终主分类器。

过程变量目前没有与视频建立样本级映射，因此单独由 **Process State Agent** 建模：从电气状态、波动动态、加料操作和设备状态四组变量中提取稳定/波动/异常/过渡工况，变化点检测和模糊规则生成过程标签，再写入知识库、案例库和 Laya-JEV 策略库。过程数据与视频帧保持独立建模，并作为过程状态先验参与诊断编排。

推荐的过程状态输出为：

```json
{
  "process_regime": "stable|transition|abnormal|unknown",
  "event_risk": 0.0,
  "anomaly_score": 0.0,
  "process_tags": [],
  "evidence_window": {},
  "alignment_quality": "exact|interval|segment|weak|unknown",
  "process_missing": false
}
```

只有未来获得可靠时间/槽级映射，或运行时同时提供过程窗口时，才允许将过程状态作为任务级晚融合上下文；过程分支必须带 `process_missing` 和 `alignment_quality` 掩码。

### 4.5 LLM 后训练、诊断聚合与证据质疑

当前 LLM 已能通过 `LLMGateway` 生成结构化 `DiagnosisDraft`，但尚无领域诊断轨迹的 QLoRA/SFT 和独立 LLM Verifier。后续采用“强教师生成 → 专家修订 → QLoRA/SFT → Verifier 偏好优化 → 冻结回放”的路线：

```text
EvidenceBundle
  → 诊断聚合 Agent（Qwen-VL + 领域 LoRA）
  → DiagnosisDraft + evidence_claims
  → Verifier Agent（独立模型/提示 + review_guard）
  → pass / amend / request_more_evidence / human_review
  → 缺失证据回补，最多两轮
  → 人工确认
```

聚合 Agent 使用视觉证据、ProcessStateSnapshot、知识命中、已审核案例和 Laya-JEV 决策作为输入；训练目标是诊断等级、风险、来源引用、检查事项和不确定性。每条 `evidence_claim` 必须绑定 `EvidenceRef`。Verifier 只读取草案与证据清单，不读取聚合模型隐藏思维链，输出支持分数、缺失来源、冲突、数值输入完整性和动作授权结果。系统对外保存 `rationale_summary`、`evidence_ids` 和问题码，不保存私有 CoT。

首版使用 LoRA/QLoRA 领域 SFT；DPO/ORPO 作为专家修订偏好训练；只有证据支持、Schema 合法性和安全检查能够形成稳定可验证奖励后，才评估 GRPO。没有专家轨迹时，规则和历史人工结论只能生成弱标注，不能作为最终效果指标。

新增训练和运行模块规划为：

```text
agentic/training/build_trace_dataset.py
agentic/training/sft_diagnosis.py
agentic/training/sft_verifier.py
agentic/agents/critic_agent.py
agentic/platform/evidence_graph.py
```

详细的样本协议、损失设计、Verifier 回补和 PPT 页面提示词见 [LLM后训练_诊断聚合质疑与Laya-JEV路由升级方案.md](ppt制作/LLM后训练_诊断聚合质疑与Laya-JEV路由升级方案.md)。

## 5. 目标角色与协作流程

### 5.1 角色定义

| 角色 | 主要输入 | 主要输出 | 实现方式 |
|---|---|---|---|
| 任务接入/安全门控 | 图片、用户说明、模型配置 | 任务 ID、输入类型、策略档位、是否允许进入识别 | 规则 + 任务协议 |
| 图像质量 Agent | 原始图片/短视频帧 | 模糊、过暗、过曝、遮挡、分辨率、跨帧质量稳定性 | OpenCV/质量模型 |
| 多帧视觉分类 Agent | 合格短视频窗口 | YOLO ROI、C/N/H 概率、风险、不确定性、动态特征、关键帧 | F-GMVAE-T：空间编码器 + 时序编码器 + 专家先验 |
| Process State Agent | 14 维过程变量及其窗口统计特征 | `event_risk`、工况状态、变化点、过程标签、证据窗口 | 时序编码器 + 变化点检测 + 模糊规则；过程状态先验 |
| Laya-JEV 编排路由 Agent | 质量信号、F-GMVAE-T 输出、案例相似度、风险和证据覆盖；可选可靠 `ProcessStateSnapshot` | `simple_loop/full_loop/retake/human` 路由、难度、置信度、原因、匹配案例、过程上下文是否使用 | Laya 开源基座 + JEV 思想适配 + 案例检索 + 确定性安全门控 |
| 工艺知识 Agent | 视觉类别、过程状态（若有）、诊断问题 | 文档片段、规则 ID、版本、来源、适用范围、检索分数 | 领域 RAG |
| 案例记忆 Agent | 视觉特征、知识查询 | 已审核相似案例及其来源/人工结论 | 只检索已批准案例 |
| 诊断聚合 Agent | 视觉证据、知识证据、案例证据、路由决策 | 固定 Schema 的研判草案、证据主张、风险、不确定性、后续检查 | Qwen-VL + LoRA/QLoRA；结构化输出 |
| 证据质疑/复核 Agent | 草案、证据清单、已知来源和安全策略 | 支持分数、无效引用、证据冲突、缺失项、越权结论、回补动作 | 独立 Verifier + 确定性 `review_guard` |
| 人工确认 Agent/操作员 | 草案、证据、复核问题 | approve/reject/request_retake/amend 与原因 | LangGraph interrupt/resume + UI |
| 归档与报告 Agent | 最终人工决策和全量结构化记录 | 可回放报告、候选案例 | 模板/存储服务 |

“图像质量”和多帧视觉编码可以并行准备；候选案例/关键规则检索在视觉结果后快速完成，供 JEV 做路由判断；进入完整路径后，视觉复核、深度知识检索、特殊案例比对和过程状态核查可以并行；诊断聚合必须等待其所需输入；规则复核位于诊断之后。人工确认是最终授权边界。

### 5.2 目标工作流

```text
创建巡检任务
  → 输入完整性/安全前置检查
  → 短视频多帧抽取与图像质量检查 ──质量不合格──→ 请求补拍并暂停
  → 多帧视觉分类（YOLO ROI + F-GMVAE-T）
  → 低成本候选检索（特殊案例 + 关键规则命中）
  → 可选运行时过程状态快照（仅限可靠对齐；历史未配对数据不直接接入）
  → Laya-JEV 编排路由器
      ├─ simple_loop：候选案例/关键规则 + 轻量报告 + 确定性复核
      ├─ full_loop：{多帧视觉复核 || 深度工艺知识检索 || 特殊案例比对 || 可选过程状态核查}
      │          → 强 Qwen-VL 诊断 → 证据质疑/复核
      ├─ retake：证据不足或图像边界 → 请求补拍并暂停
      └─ human：高风险、冲突或路由异常 → 人工复核
  → simple_loop/full_loop 结果统一进入安全校验和人工确认
  → approve / amend / reject / request_retake
  → 保存报告、审核轨迹、Laya-JEV 路由记录和候选特殊案例
  → 候选案例经冻结集评测与授权后再进入正式特殊案例库
```

简单小循环不是跳过安全边界：它只减少不必要的强模型和协作节点，仍然要引用适用的工艺知识、执行确定性证据检查，并按项目要求进入人工确认。它适用于“已有可靠特殊案例或规则、视觉证据稳定、低风险、无需多角色互相质疑”的任务。完整大循环用于复杂、陌生、边界、证据不足或高风险任务，至少包括多源取证、知识检索、案例比对、强模型诊断和证据质疑。两条循环最后使用同一个诊断 Schema、复核器和审核状态机，便于回放和公平评测。这是一条短视频窗口任务流程状态机，不代表长周期火眼时序预测。每次状态迁移应记录事件、时间、角色、模型版本和输入/输出摘要；日志不保存模型私有思维链。

## 6. 统一协议与模型调用边界

沿用并逐步落实现有协议，确保角色间交接是数据契约而不是自由文本：

- `InspectionTask`：run_id、输入引用、session/tenant、模型策略、任务时间和运行状态。
- `AgentResult`：agent_id、状态、结构化输出、证据列表、问题列表、模型元数据和耗时。
- `EvidenceRef`：证据类型、图像 ROI/关键帧或规则/文档定位、source_id、版本、引用片段、置信度。
- `VisualTemporalResult`：窗口帧引用、C/N/H 概率、风险、不确定性、静态/动态特征、跨帧一致性和关键证据帧。
- `ProcessStateSnapshot`：过程窗口、工况状态、异常分数、过程标签、对齐质量和缺失掩码；未配对数据只能作为离线状态记录。
- `ReviewDecision`：审核人、动作、修改、原因、时间和被审核结果版本。
- `TraceEvent`：节点开始/完成/错误/重试/升级/降级事件。
- `JevRouteDecision`：诊断循环路由、难度、陌生度、置信度、风险、候选案例、证据缺口、原因、模型 profile 和策略版本。

诊断模型输出限定为 JSON Schema，例如 `visual_summary`、`visual_evidence[]`、`knowledge_evidence[]`、`risk_interpretation`、`uncertainties[]`、`follow_up_checks[]`。模型客户端负责供应商适配与超时/错误归一化；业务节点只请求“具备视觉能力、JSON 输出能力”的模型 profile，不直接知道 Ollama、DashScope 或 URL 细节。

模型调用失败时按顺序处理：有限重试 → 更换配置的备用 profile（如允许）→ 生成明确标记的视觉模型草稿/unknown → 人工复核。Fallback 结果不能伪装成正常模型成功，也不能被规则复核自动通过。

## 7. 知识与案例体系

### 7.1 领域知识

首批知识优先覆盖：

- 过热度物理定义、可用输入和数值计算边界；
- C/N/H 等视觉标签对应的定义、可观察征兆和禁用推断；
- 经审核的铝电解工艺规程、检查 SOP、异常处理规范；
- 规则 ID、前置条件、所需输入、适用槽型/工况、来源、版本、发布日期和有效期；
- 证据不足、规则冲突、文档过期时的拒答或升级策略。

检索升级分层实施：当前本地词面检索 → BM25/向量混合检索 → Reranker → 需要多服务协作时再评估 MCP/Milvus。先建立可信、可版本化的领域语料，再评估索引规模；不要为技术名词提前引入尚无知识量支撑的基础设施。

### 7.2 案例记忆

特殊案例库用于 Laya-JEV 的快速命中和完整流程的案例比对，不是未经审核的聊天记忆。每个案例至少保存：`case_id`、原图/ROI 哈希、视觉特征、场景与槽型、可见征兆、风险等级、适用条件、允许引用的知识来源、人工结论、现场审核事项、建议动作、模型 profile、知识/提示词版本和审核时间。

所有模型运行结果先进入候选案例区，并标记 `candidate`。只有人工批准、证据来源完整且通过冻结回归集的案例，才能进入 `approved_special_case` 正式库；被驳回、补拍、无匹配或知识缺失的任务保留为负例和拒答评测样例。正式案例还应支持 `active`、`deprecated`、`eval_only` 等状态，避免过期规则继续参与 Laya-JEV 分流。

案例沉淀是持续运行的闭环：每次任务都可以产生候选特殊案例，审核人员补充标签和现场核查结果后再进入回归评测；通过评测且满足适用范围的案例才发布新版本。相似度命中不能单独放行高风险任务，Laya-JEV 还必须检查风险、适用条件、证据完整性和案例版本；命中冲突或条件不满足时，统一转入完整流程或人工复核。

### 7.3 非配对过程数据

当前过程数据是独立的多变量时序集合，无法和火眼视频建立帧级、区间级或槽级对应关系。因此它不进入当前视频分类器的监督样本，也不用于声称视觉-过程融合精度提升。建议先建立过程状态数据集和独立评测：

#### 7.3.1 `Code/data/v1` 过程状态数据资产

当前 `v1` 已具备一条完整的过程事件预警基线链路，可作为 Process State Agent 的第一版训练与评测数据：

| 项目 | 当前资产 |
|---|---|
| 原始与清洗数据 | `Cleaned_PotData.csv`、`Tenrpt100_Data.csv`、`tenrpt100_merged_clean.csv`、按月 selected CSV |
| 设备范围 | 单槽 `potName=8310`；全周期约 145,030 条、约 2 分钟采样记录 |
| 输入变量 | 从 14 个过程变量中选择电气状态、波动动态、加料操作和设备状态特征；当前字段以过程代理变量为主 |
| 样本窗口 | `X_seq=(5744, 30, 14)`；30 步历史 × 2 分钟 = 60 分钟历史窗口 |
| 统计特征 | `X_stat=(5744, 70)`，与序列窗口对应的统计/趋势特征 |
| 预测目标 | `y` 二分类过程事件预警；15 步 × 2 分钟 = 未来 30 分钟事件状态 |
| 时间切分 | train：2021-11-01～11-20；val：11-21～11-25；test：11-26～11-30 |
| 标签规模 | 全部样本 `y=0:2651`、`y=1:3093`；切分文件为 `step2_ew_202111/split.json` |

已有 baseline 位于 `step3_baseline_202111`：

| 模型 | Test ROC-AUC | Test PR-AUC | Test F1@0.5 | 备注 |
|---|---:|---:|---:|---|
| CNN（序列 + 统计特征） | 0.542 | 0.591 | 0.656 | 验证集阈值校准后召回率 0.991、精度 0.537 |
| 1D-CNN | 0.527 | 0.562 | 0.642 | 验证集最优阈值为 0.01 |
| LSTM | 0.437 | 0.481 | 0.600 | 验证集阈值迁移后出现全正类预测 |

这组结果的定位是 **过程事件预警与状态先验 baseline**。下一步由 Process State Agent 输出 `event_risk`、`operating_regime`、`change_points`、`process_tags` 和 `evidence_window`，供工艺知识、特殊案例和 Laya-JEV 使用。现有 `state_mask` 是 bitmask 编码，`event_id` 对应大量短事件段；建模时先按连续事件段和状态掩码归并为稳定工况标签，再扩展多类状态。评测优先采用时间切分、事件级 PR-AUC/Recall、提前预警时间、概率校准和按槽位分组验证；当前单槽、单月训练集用于流程验证和模型对照，不作为跨槽泛化结论。

推荐的过程变量分组如下，最终输入由训练集上的稳定特征选择和工艺专家复核共同确定：

| 变量组 | `v1` 字段 | Process State Agent 的作用 |
|---|---|---|
| 电气状态 | `potVolt`、`potCurrent`、`settingVolt`、`settingVoltMin`、`settingVoltMax` | 表征槽电压、电流和设定边界 |
| 波动与动态 | `fluctDelta`、`wavingDelta`、`slopeData`、`sumSlopeData` | 表征波动幅度、趋势和变化点 |
| 加料操作 | `baseFeedingInter`、`actualFeedingInter`、`feedingState` | 表征加料节奏、执行间隔和操作状态 |
| 设备状态 | `aeWaitInterval`、`andoeMoveState` | 表征事件等待状态和阳极移动状态；当前 `andoeMoveState` 覆盖度有限 |

对每组变量提取窗口均值、标准差、端点差、斜率、变化率、波动幅度和缺失模式，并保留 `X_seq` 的原始序列输入。首版建议使用 `potVolt`、`potCurrent`、`fluctDelta`、`wavingDelta`、`slopeData`、`sumSlopeData`、`actualFeedingInter` 和 `feedingState` 构建紧凑特征集；`feedingState` 与 `andoeMoveState` 按类别/事件上下文编码，避免作为连续物理量解释。`settingVoltMin/Max`、`aeWaitInterval`、`baseFeedingInter` 和数据覆盖充分后的 `andoeMoveState` 作为边界与扩展配置，通过 permutation importance、SHAP、时间滚动验证和专家复核确认变量贡献。

因此，过程分支的领域表述统一为“多变量过程状态建模”和“过程事件风险先验”，不将当前字段包装成未实际采集的化学浓度测量量。

- 按槽号、日期或可用工况字段切分时序窗口，避免相邻窗口泄漏；
- 训练过程状态 Agent 识别稳定、波动、异常和过渡工况；
- 对上述电气、波动、加料和设备状态变量提取累计量、变化率、斜率、波动幅度和变化点；
- 用模糊 IF-THEN 规则生成过程标签，并保留原始窗口和来源字段；
- 将结果写入知识库、案例库和 Laya-JEV 策略库，作为过程先验而不是视频标签。

推荐的对齐等级为 `exact`、`interval`、`segment`、`weak`、`unknown`。只有运行时同时提供过程窗口且对齐等级达到预设门槛时，才允许任务级晚融合；其余情况保留 `process_missing` 或 `alignment_quality`，不得用最近值、同日值或随机窗口制造伪配对。

## 8. 实施路线

| 阶段 | 主要工作 | 阶段验收 |
|---|---|---|
| P0：模型网关与协议打通 | 抽象统一多模态 JSON 调用接口；接入现有 OpenAI 兼容客户端；建立本地 Ollama、至少一种 Qwen 云端视觉模型和文本模型 profile；Agent 诊断/复核可按配置切换 | 同一输入可在至少两类 provider/profile 运行；保存真实模型信息；密钥不进 Git；失败与超时状态可见 |
| P1：角色合同与安全门控 | 统一 AgentResult/EvidenceRef；图像质量检查；输入完整性和低证据路由；固定诊断 Schema 与越界规则 | 模糊、无目标、缺失模型或知识的样本可稳定进入拒答/补拍/人工分支 |
| P1.5：多帧视觉与过程解耦 | 实现短视频窗口、YOLO 逐帧 ROI、空间-时序编码器、F-GMVAE-T 输出；独立 Process State Agent 建模未配对过程数据；加入 `process_missing/alignment_quality` | 单帧/多帧/F-GMVAE-T 可对照；过程状态可独立评测；没有可靠映射时不会产生伪配对 |
| P2：JEV 思想适配与 Laya-JEV 编排 | 在低成本视觉初筛后接入 Laya-JEV；实现 simple_loop/full_loop/retake/human 四路策略；视觉质量/检测并行；知识/案例检索并行；诊断前聚合；按置信度、风险和任务类型选择模型档位 | 页面可见 Laya-JEV 输入、路由后端、路由理由、匹配特殊案例、各诊断循环耗时/状态；复杂样本进入完整大循环的召回率达标；结果可回放 |
| P3：领域 RAG 与来源治理 | 导入经授权的铝电解 SOP/知识；增加来源、版本、适用范围；实现混合检索及可选重排；完成引用校验 | 每条领域结论可回到有效来源；知识缺失和过期规则可识别；无有效证据时拒绝强答 |
| P4：真实 HITL 与任务历史 | LangGraph interrupt/resume；Streamlit 审核操作；审核原因、修改、结果发布和报告导出；运行历史查询 | 审核暂停后可恢复；批准/修改/驳回/补拍都形成审计记录并与 run_id 关联 |
| P5：冻结评测与申报材料 | 专家标注冻结集、模型/profile 对照、工作流消融、运行健康评测、可重复报告 | 有可复现的配置、数据切分、指标、失败案例和系统演示；结论不越出现有数据支持范围 |
| P6：受控扩展 | 在评测基础上引入 RSI 的经验分析/候选提示或知识变更；评估 DeepSeek SuperAgent 式任务面板/Worker 设计 | 任何演化都限定修改边界、保留版本谱系、通过冻结评测和人工批准后才晋级 |

P0 到 P5 是形成申报级闭环的主线。JEV 是 P2 所参考的诊断路径选择思想，Laya-JEV 是其在本项目中的领域适配效率层；它不是视觉分类器或最终诊断器，阈值和策略必须随冻结评测版本化。RSI 和 SuperAgent 是后续扩展主题，不作为打通主系统的前置条件；也不让 Agent 在线自动改写模型权重、工艺规则或批准结论。

## 9. 评测设计

评测分为领域效果、安全边界、多智能体协作和系统健康度四层。视觉分类增加单帧/多帧/F-GMVAE-T 对照；过程状态单独评测；没有样本级映射时不报告视觉-过程融合指标。所有模型档位使用相同冻结案例、提示版本和判分协议，避免数据或提示差异造成不公平比较。

### 9.1 数据与标注

建立至少以下案例类别：清晰/低质量图像、目标存在/缺失、各视觉类别、边界样本、知识充分/知识缺失、来源冲突、模型超时/格式错误。由领域人员标注：图像质量、目标位置、可见征兆、视觉类别/风险意见、必要证据、是否补拍、是否需人工升级、允许引用的知识来源。多位专家的分歧单独记录，不把争议样本硬标为唯一真值。

### 9.2 指标

| 维度 | 推荐指标 |
|---|---|
| 领域研判 | 可见异常/风险点 Issue Recall、Precision/F1；视觉类别 Accuracy/Macro-F1/混淆矩阵；风险等级与专家一致率 |
| 多帧视觉分类 | C/N/H Macro-F1；跨帧一致性；动态征兆识别；关键证据帧定位有效率；不确定性 ECE/Brier |
| 过程状态 Agent | 工况状态识别、变化点检测、异常召回率、过程标签一致率；与视频未配对时不计算跨模态准确率 |
| 证据质量 | 证据链完整率；图像证据定位有效率；引用存在率和引用支持率；无来源结论比例 |
| 安全边界 | 无测量条件下数值过热度拦截率；越权工艺指令拦截率；低质量/无目标的拒答或补拍召回率 |
| Agent 协作 | 端到端流程完成率；结构化交接成功率；节点失败/重试/Fallback 率；冲突升级准确率；人工修改/采纳比例 |
| 系统健康 | P50/P95/P99 总延迟与分角色延迟；首次响应时间；超时/异常率；每次任务 Token/成本；模型 API 可用性 |

JEV 需要单独作为诊断编排路由器评测：简单案例进入 `simple_loop` 的 Precision/Recall，复杂案例进入 `full_loop` 的召回率，高风险或危险样本误进入 `simple_loop` 的漏放率，两个诊断循环的平均时延与 Token 降幅，特殊案例命中率，以及人工改判率。申报材料中应优先报告危险样本漏放率和复杂样本进入完整大循环的召回率，再报告平均效率收益；不能只用平均时延下降证明分流有效。

没有连续温度、成分和初晶温度真值时，不使用过热度数值 MAE 作为核心效果指标。不要把 `evidence_review_passed` 说成专家认定或诊断正确，只能表示规则检查通过。

### 9.3 必做对照/消融

- 现有视觉模型 + 规则结果作为任务基线；
- 单帧 ResNet 基线 vs 单帧 ConvNeXt/轻量 ViT；
- 单帧视觉 vs 多帧视觉时序编码；
- 多帧视觉 vs 多帧 + 静态/动态专家特征；
- 多帧 + 专家特征 vs F-GMVAE-T；
- 视觉主模型 vs 视觉主模型 + 独立过程状态 Agent（仅比较路由、解释和案例检索，不声称样本级融合提升）；
- 仅视觉诊断 vs 视觉 + 工艺知识；
- 小型本地视觉模型 vs 云端 Qwen 视觉 profile；
- 单次多模态诊断 vs 诊断 + 独立证据复核；
- 词面检索 vs 混合检索/重排（语料准备后）；
- 固定模型路由 vs 质量/置信度驱动的升级策略；
- 无 JEV 全部大循环 vs JEV simple_loop/full_loop 编排；
- 仅相似度命中 vs 相似度 + 风险/适用条件/证据门控；
- 有/无图像质量门控、有/无人工复核。

申报汇报应同时报告质量、失败、延迟和成本，不只挑选最强模型分数。不同模型档位的 API 模型名称、调用日期、参数和服务区域需要写入结果元数据。

## 10. 申报创新点与应用价值

建议凝练为以下四点，并用系统实现与评测证据支撑：

1. **多帧视觉证据与工艺文本知识协同**：YOLO 多帧 ROI、空间-时序编码器和 F-GMVAE-T 形成动态视觉证据，再与版本化工艺知识和多模态模型通过统一证据协议交互。
2. **非配对过程数据的解耦建模**：对未能与视频对齐的 14 维过程变量及其派生状态特征独立建模，形成工况状态、过程事件风险和过程先验。
3. **面向工业风险的可审计协作**：不确定性识别、证据质疑、越界拦截、失败降级和强制人工确认进入同一任务状态机。
4. **多模型按角色配置与受控升级**：本地模型和不同能力档位的 Qwen API 可配置选择；以冻结评测衡量能力收益、延迟和调用成本，避免模型越大越好的主观结论。
5. **Laya-JEV 诊断编排与特殊案例记忆闭环**：以 JEV 参考思想为路径选择原则，用 Laya 基座适配轻量路由器，把高置信度、低风险、已有可靠案例的任务送入简单小循环，把复杂、陌生、冲突和高风险任务送入完整大循环；人工审核后的特殊案例再经过冻结评测和版本治理，反哺后续编排。

应用场景表述为铝电解槽火眼巡检的图像辅助研判、证据归档、异常复核和专家案例积累。没有现场使用数据前，不声称已减少停槽、优化控制或提升实际产能。

## 11. 主要风险与控制

| 风险 | 控制方式 |
|---|---|
| 视觉征兆被误当作数值过热度 | Schema 和规则禁止无测量输入输出摄氏度/ΔT；UI明确显示视觉代理标签 |
| 大模型 API 型号或接口变化 | 模型注册表和可配置 profile；启动时能力探测；保存模型 ID/调用版本；保留本地回退 |
| 云端图像数据边界不清 | 提供本地模式；云端调用前可做 ROI 裁剪/脱敏；设置页显示当前 provider；密钥只存环境变量 |
| 多 Agent 仅增加调用和展示，没有功能收益 | 对照/消融证明角色分工带来证据完整、拒答安全或专家可用性改善；无收益的 Agent 合并为工具节点 |
| 检索引用看似正确但不支持结论 | source ID、版本和片段绑定；引用支持率纳入冻结评测；过期/不适用知识阻断自动放行 |
| 案例记忆污染知识库 | 案例分候选/已审核/冻结评测；修改需审核和回归；评测集永不进入检索/演化语料 |
| 云模型调用成本/延迟上升 | 按任务复杂度路由；小模型初筛，难例才升级；记录 Token 与时延；人工/规则结果有明确降级方案 |
| JEV 把复杂或危险样本误分到简单小循环 | 设置保守阈值；高风险、冲突、无可靠案例和边界质量一律 full_loop/human；把危险样本漏放率纳入发布门槛 |
| 特殊案例相似但适用条件不一致 | 相似度必须与槽型/工况/风险/证据条件联合判断；条件不满足时不得快速放行；案例版本过期自动失效 |
| 过程数据被错误地与视频伪配对 | 记录 `alignment_quality`；无可靠槽号/时间窗/工况映射时只做独立过程建模；禁止最近值、同日值或随机窗口拼接 |
