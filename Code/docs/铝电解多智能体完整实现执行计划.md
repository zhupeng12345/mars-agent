## 1. 交付目标

最终交付不是一张架构图，而是一套可以从视频或图片开始运行的本地系统：

```text
视频/图片任务
  → 输入完整性与图像质量门控
  → 多帧抽取、YOLO ROI、视觉时序分类
  → Process State Agent（独立过程状态分支）
  → 特殊案例/工艺规则低成本检索
  → Laya-JEV 诊断编排
       ├─ simple_loop：轻量诊断 + 确定性复核
       ├─ full_loop：多 Agent 并行取证 + 聚合 + 证据复核
       ├─ retake：请求补拍并暂停
       └─ human：人工直接复核
  → 统一诊断 Schema
  → 人工 approve/amend/reject/request_retake
  → 报告、审计轨迹、候选特殊案例
  → 冻结评测与 RSI 离线候选演化
```

### 1.1 完成定义（Definition of Done）

只有同时满足下列条件，才可以在汇报中称为“完整版本”：

1. 同一任务可在本地 Ollama 和至少一种 OpenAI 兼容的 Qwen API profile 上运行，实际 provider、model、版本、耗时和失败状态会被记录。
2. 图片和短视频都经过质量门控；质量不足、无目标、输入损坏或缺少必要模型时有明确的 `retake`/`human` 路径。
3. 视频可以抽取固定多帧窗口，逐帧完成 ROI 检测/跟踪，并输出视频级视觉证据；单帧/多帧/F-GMVAE-T 有可复现对照。
4. `Code/data/v1` 的 14 维过程变量由独立 Process State Agent 运行并评测；没有可靠时间或槽位映射时不会伪造视频配对。
5. Laya-JEV 能基于 JEV 参考思想和结构化证据选择 `simple_loop`、`full_loop`、`retake`、`human` 四路，并在网页端显示路由原因、置信度、风险和匹配案例。
6. `full_loop` 至少有视觉复核、工艺知识 RAG、特殊案例比对、Process State Agent 四类协作节点，支持 fan-out/fan-in、超时和有限重试。
7. 所有 Agent 通过统一协议交接，诊断、证据、复核和人工决策都绑定 `run_id/thread_id`，可以重放一次运行。
8. 人工审核可以真实暂停并恢复 LangGraph 任务；approve、amend、reject、request_retake 都会形成审计记录。
9. 评测脚本可以重新生成视觉、过程状态、Laya-JEV 路由、协作健康度和消融结果；没有数据支持的数值过热度和生产控制结论不会被输出。
10. PPT 所需图片全部来自真实数据、真实运行轨迹或可复现绘图脚本，图片有来源、运行 ID、版本和生成命令。

### 1.3 本轮执行顺序与阶段闸门

本轮以“先完整链路、再前端展示、后增强优化”为唯一执行顺序。每个阶段先完成可复现验收，再进入下一阶段；页面截图不能替代链路验收。

**E0：完整诊断链路跑通（前端之前）**

```text
图片/视频
  → 媒体标准化与质量门控
  → 多帧 ROI/视觉证据
  → 独立 Process State Agent（有过程输入才运行）
  → 工艺知识与已审核案例检索
  → Laya-JEV 路由
  → simple_loop 或 full_loop
  → 诊断聚合与证据复核
  → interrupt 等待人工
  → approve/amend/reject/request_retake
  → 报告、审计和候选案例
```

E0 的验收输入至少包括一张真实图片、一段真实视频和四个路由 fixture。验收必须留下 `run_id/thread_id`、每个节点的结构化输入输出、Laya-JEV 路由原因、fan-out/fan-in 结果、人工决定和可回放报告；页面尚未接入时可用 CLI/JSON 完成，但不能只用静态模拟数据。Laya-JEV 在此阶段采用“JEV 参考思想 + Laya 可选基座 + 确定性门控 + fallback”的实现边界，不能把尚未有专家路由标签的 Laya fit 结果写成已训练模型。

**E1：前端工作台与回放展示**

E0 通过后再接入网页。网页必须展示输入媒体/代表帧、多帧 ROI、质量分数、视觉证据、Process State 和对齐质量、Laya-JEV 路由及理由、simple/full 分支、并行 Agent 状态、知识/案例引用、诊断 JSON、复核问题、人工按钮、`run_id/thread_id`、模型/知识/提示词版本和报告导出。刷新或服务重启后，使用相同 `thread_id` 恢复人工审核；点击运行不能出现无事件的持续转圈。

E1 的验收以本地 Streamlit 实际运行和四路 fixture 截图为准。每张截图必须有同名 JSON sidecar，记录来源文件、运行 ID、版本和生成命令；流程验证结果标记为 `flow_validation`，不写成视觉精度或真实过热度结果。

**E2：增强优化与申报级评测**

E1 通过后再补充 Laya fit/calibration、过程状态学习 baseline、真实专家标注下的多帧/F-GMVAE-T 训练、混合 RAG/Reranker、RSI 离线候选演化、消融实验和 25 页 PPT 资产。任何增强都必须带数据版本、切分、模型/profile、知识版本、随机种子和失败样例；无专家视频标签、GPU 或可靠视频-过程对齐时，保持 `structure_only`/`experimental` 状态，不虚构指标。

阶段状态约定：`implemented` 表示已有代码和通过验收；`flow_validation` 表示链路/界面可运行但效果未获真值支持；`experimental` 表示有实验入口但尚未完成研究验收；`blocked_external` 表示需要专家标注、GPU、API key 或可靠数据映射。Codex 每次只推进一个阶段，完成后更新 `Code/docs/implementation_log.md`，再继续下一阶段。

## 2. 执行纪律

### 2.1 Codex 每次执行规则

每次开始前先读取本文件中对应的阶段和任务编号，再执行以下动作：

1. 检查工作区状态：`git status --short`，不覆盖用户已有修改。
2. 阅读任务涉及的现有文件和调用方，确认接口后再编辑。
3. 只修改当前任务需要的文件；新模块要有最小单元测试或可执行 smoke test。
4. 不把规划代码、模拟数据和真实完成能力混在一起；代码、页面和文档中使用 `planned`/`experimental`/`implemented` 明确状态。
5. 运行阶段验收命令，并把命令、结果、失败样例和未解决问题写入 `Code/docs/implementation_log.md`。
6. 通过阶段闸门后，才更新本计划的状态复选框和 PPT 页面状态。

### 2.2 不允许的捷径

- 不随机切分相邻视频帧来制造高指标；视频按视频/场景/任务分组切分。
- 不把文件名“正常/偏高”直接当作专家真值；它只能记录弱标签。
- 不把未配对过程数据拼接到视频帧上，也不使用最近值、同日值或随机窗口伪造对齐。
- 不让大模型直接生成加料、调压或其他生产控制指令；最终授权始终由人工节点持有。
- 不把 `evidence_review_passed` 写成“诊断正确”或“实测过热度准确”。
- 不把未经过评测和人工批准的运行结果直接放入正式特殊案例库。
- 不在线自动修改模型权重、工艺规则、提示词生产版本或人工批准结果。

### P0.3 LLM Gateway 和 profile

**目标**：统一接入本地 Ollama、OpenAI 兼容 Qwen API 和测试用 fake provider。

**修改范围**：新建 `Code/agentic/platform/llm_gateway.py`、`Code/config/agent_profiles.yaml`（或 JSON），复用 `Code/llm_api_client.py` 的认证和请求逻辑，但不在工作流节点中复制 HTTP 调用。

**最小接口**：

```python

    profile="local_fast",
    messages=messages,
    images=roi_images,
    response_schema=DiagnosisSchema,
    trace_context=trace_context,

```

**必须记录**：provider、model、profile、capabilities、request ID、耗时、token usage（能取到时）、重试次数、错误类型、fallback profile。

**结构化输出约定**：诊断模型只生成 `DiagnosisDraftPayload`，`run_id/thread_id`、Agent 元数据和 EvidenceRef 由本地流程补齐。Ollama 收到该 payload 的 JSON Schema 并在本地二次校验；OpenAI 兼容 profile 默认使用 `json_object`，只有目标模型/API 支持时才配置 `structured_output_mode=json_schema`。拒答、截断、非 JSON 和 schema 校验失败均生成明确错误状态，不保存模型私有推理内容。

**通过标准**：

- 同一结构化任务可以选择 `fake_json`、`ollama_local` 和 `qwen_api` profile；
- 没有 API key 时 qwen profile 返回可见的 `configuration_error`，不会卡住流程；
- 真实 key 只来自环境变量或 `.env`，不写入 Git；
- 至少完成一次本地模型 smoke test；Qwen API smoke test 在有 key 时执行，没有 key 时保留明确跳过记录；
- 超时、非 JSON、HTTP 错误和模型能力不匹配均能被统一捕获。
- provider 支持结构化 JSON Schema 时传入同一 payload schema；不支持时保留 JSON mode 并执行本地严格校验。

## 8. P2：JEV 思想适配、Laya-JEV 编排与 simple/full loop

### P2.1 JEV 参考思想和 Laya-JEV 决策协议

JEV 在本项目中表示参考的证据驱动路径选择思想；实际工程路由器采用 Laya 开源基座进行可选适配，外层由确定性安全门控和 LangGraph 条件路由约束，统一命名为 `Laya-JEV`。因此代码、日志和 PPT 中不得把 Laya-JEV 写成“官方 JEV 模型”，也不能把 Laya 的预测结果描述为 C/N/H 分类结果。

**输入特征**：图像质量、ROI 覆盖、视觉置信度、跨帧一致性、OOD/新颖性、风险、知识覆盖度、案例相似度、证据冲突、过程状态快照（仅在可靠映射时）。

**输出**：

```json
{
  "route": "simple_loop|full_loop|retake|human",
  "difficulty_score": 0.0,
  "novelty_score": 0.0,
  "confidence": 0.0,
  "risk_level": "low|medium|high|unknown",
  "similar_case_ids": [],
  "evidence_gaps": [],
  "reasons": [],
  "process_context_used": false,
  "alignment_quality": "unknown",
  "model_profile": "laya_jev_router_v1",
  "gate_version": "laya-jev-policy-0.1"
}
```

Laya-JEV 只决定诊断循环，不决定 C/N/H，不给出摄氏度过热度，不替代人工确认。确定性安全规则优先于 Laya 输出；Laya 不可用、低置信度、`abstain`、`unbound`、未知 route 或超时均进入 `full_loop`/`human` 安全 fallback。

### P2.2 规则基线和路由训练集

**任务**：

- 先实现可解释规则：高风险、边界质量、证据冲突、无可靠案例一律 `full_loop` 或 `human`；质量不合格进入 `retake`。该规则层是 Laya-JEV 的安全前置，不依赖 Laya 是否安装。
- 实现 `LayaAdapter` 和可选 HTTP adapter；记录 provider、Laya 版本、策略版本、概率/abstain 状态和 fallback 原因。
- 建立 `route_annotation_template.jsonl`，让专家标注“应走哪条循环、为什么、所需证据、风险等级”。
- 训练集没有专家路由标签时，只报告规则 smoke test 和弱标签实验，不把规则结果称为专家准确率。
- 后续可用 LightGBM/XGBoost/逻辑回归/小型 MLP 训练路由器，并进行温度校准。

**通过标准**：每个路由结果有 `reason`、`gate_version`、`router_backend` 和输入特征快照；相同输入和策略版本得到相同路由；Laya-JEV 异常时默认走 `full_loop`/`human`；没有专家路由标签时报告明确标注 `rule_validation` 或 `structure_only`。

### P2.3 simple_loop

**流程**：已审核案例/关键规则检索 → 轻量诊断摘要 → 确定性证据检查 → 统一复核 → 人工确认。

**通过标准**：低风险、证据充分、适用案例明确的样本可少调用节点；复核发现冲突时自动升级 `full_loop`；simple loop 不绕过知识引用和人工确认。

### P2.4 full_loop fan-out/fan-in

**并行节点**：

- 多帧视觉复核 Agent；
- 图像质量/证据完整性 Agent；
- 工艺知识 RAG Agent；
- 特殊案例比对 Agent；
- Process State Agent（有运行时窗口时）。

**汇聚节点**：诊断聚合 Agent → 证据质疑/复核 Agent → 统一人工门控。

使用 LangGraph 的并行发送或受控 `asyncio.gather`；记录每个子节点的开始/结束/错误/重试，并设置最大轮次、超时和取消策略。

**通过标准**：至少两个独立 Agent 能并行运行；一个子 Agent 失败不会丢失其他结果；证据缺失会触发补取、升级或人工；无条件无限循环；trace 能还原 fan-out/fan-in 顺序和耗时。

### G2 阶段闸门

同一输入至少演示四种路由：简单、复杂、低质量、直接人工。页面显示 Laya-JEV 输入特征、路由理由、循环名称、后端类型（规则/Laya/HTTP/fallback）、并行节点状态和总耗时。评测中优先报告复杂样本进入 `full_loop` 的召回率和危险样本误入 `simple_loop` 的漏放率，再报告平均 Token/时延收益；没有专家路由真值时，仅报告 fixture 覆盖和流程验证。

## 11. P5：冻结评测、消融和健康度报告

### P5.1 数据集冻结

建立以下清单，禁止评测集参与案例库或 RSI 演化：

```text
Code/data/evaluation/visual_manifest.jsonl
Code/data/evaluation/process_manifest.jsonl
Code/data/evaluation/route_manifest.jsonl
Code/data/evaluation/knowledge_queries.jsonl
Code/data/evaluation/case_queries.jsonl
Code/data/evaluation/hitl_cases.jsonl
```

视觉集包含清晰/低质量、目标存在/缺失、各类别、边界和 OOD；路由集包含 simple/full/retake/human 的专家意见和理由；知识集包含有效、过期、冲突和空检索问题。

### P5.2 指标实现

**视觉**：Macro-F1、混淆矩阵、跨帧一致性、关键帧定位、ECE/Brier。
**过程状态**：事件级 Recall、PR-AUC、提前预警时间、状态一致率、校准。
**证据质量**：证据链完整率、引用存在率、引用支持率、无来源结论比例。
**Laya-JEV**：simple Precision/Recall、复杂进入 full 的召回率、危险样本 simple 漏放率、人工改判率、特殊案例命中率、Token/时延降幅；没有专家路由标注时仅报告 fixture 覆盖和流程验证。
**系统健康**：端到端 P50/P95/P99、节点耗时、超时率、失败/重试/Fallback 率、结构化交接成功率、人工采纳/修改比例。

### P5.3 必做消融

1. 单帧 baseline vs 多帧时序编码；
2. 多帧 vs 多帧 + 静态/动态专家特征；
3. 专家特征 vs F-GMVAE-T；
4. 无过程状态 Agent vs 有过程状态 Agent（只评价路由、解释、案例检索，不声称视频分类提升）；
5. 无路由全部 full loop vs Laya-JEV 分流；
6. 无案例门控 vs 相似度 + 风险 + 适用条件门控；
7. 词面检索 vs 混合检索/重排；
8. 无人工复核 vs 人工复核；
9. 本地模型 profile vs Qwen API profile。

### G5 阶段闸门

一条命令能够在干净环境重新生成指标 JSON、表格、图和失败样例；结果中包含数据版本、切分、模型/profile、提示词、知识版本、随机种子和调用日期；报告明确区分视觉状态、过程事件风险和真实过热度测量。

## 12. P6：RSI 受控离线演化

### P6.1 候选变更生成

RSI 读取运行日志、人工修改、路由改判、知识缺口、失败案例和评测结果，只生成候选变更：

- JEV 阈值/规则候选；
- Agent 提示词候选；
- RAG 查询模板候选；
- 案例索引和适用条件候选；
- 复核规则候选；
- 报告模板候选。

每个候选保存 diff、来源 run_id、生成模型、生成时间、目标指标和风险说明。

### P6.2 冻结、审核和发布

候选变更必须依次经过：离线回放 → 冻结集评测 → 失败案例审查 → 专家批准 → 版本发布 → 新旧版本对照观察。RSI 不直接修改线上模型权重、生产规则或人工结论。

### P6.3 受控运行时消费

已发布的 RSI snapshot 只能通过显式 registry 进入本地诊断运行时，并且按代码白名单解析三类运行面：JEV 的单调置信度阈值、诊断聚合器的登记提示词变体、知识检索的少量附加词。任意自由文本提示词、未知 surface、模型权重、安全规则和人工结论均拒绝执行并回退 `base`。运行结果必须记录版本 ID、内容哈希、提示词变体和查询词集合，rollback 后下一次任务恢复上一版本。

### G6 阶段闸门

使用一批历史运行记录生成至少一个候选变更；页面能展示候选 diff、评测前后指标和审批状态；未批准版本不会影响在线 JEV 或知识库；已发布版本可回滚。

### 19.3 视觉模型实施顺序和代码迁移

#### M1：单帧 baseline

- 输入：图片目录中的统一尺寸 ROI；目录标签仅作为弱/待审核标签。
- 模型：当前 YOLO + ResNet 结果作为历史基线；新增 ConvNeXt-Tiny 或轻量 ViT + 线性头。
- 输出：logits、概率、类别、校准温度、证据帧。
- 验收：按源视频/连续片段分组切分，输出 Macro-F1、混淆矩阵、ECE、失败样例；不把相邻帧随机分到不同集合。

#### M2：多帧池化/GRU/TCN baseline

- 从 `Code/model/twoChannel/model_file/CrossModelViews.py:48-98` 提取 `TemporalEncoder` 到 `Code/agentic/models/temporal.py`。
- 保留 `cnn`、`gru`、`tcn` 三种实现，统一 `forward(x: [B,T,D]) -> [B,D_out]`；原文件的 `(N,L)` 图节点接口通过 adapter 兼容，不直接改写旧实验。
- 先做 mean/max pooling，再做 GRU/TCN，验证时序分支本身是否有贡献。
- 为每个实现补 shape test、mask test、短序列 test 和 deterministic seed test。

#### M3：视频 backbone baseline

- 用 PyTorchVideo 的 X3D 或 MMAction2 的 TSM/轻量 TimeSformer 之一；先冻结 backbone，仅训练分类头。
- 视频窗口样本少时不从头训练 VideoMAE；VideoMAE 仅作为冻结特征实验，保留 CC BY-NC 4.0 许可和引用。
- 输出必须通过本地 `VisualEvidence`，不能直接把第三方模型 logits 写入诊断报告。

#### M4：F-GMVAE-T

建议文件：`Code/agentic/models/fgmvae_temporal.py`、`Code/agentic/models/losses.py`、`Code/agentic/training/train_fgmvae.py`。

从论文和毕业论文抽出的最小组件应拆开实现，便于逐项消融：

```text
FeatureLabelGenerator
  → 规则/聚类产生静态、动态、过程特征的 soft membership
GaussianMixturePrior
  → K 个单模态高斯 + soft membership 加权形成 GM prior
FuzzyGuidedVAE
  → image posterior、feature-guide prior、KL、标签/图像对比损失、分类/重构头
FGMVAETemporal
  → T 帧 image posterior + temporal pooling + temporal consistency + uncertainty
```

首批专家特征按论文可解释定义实现：

- 静态：灰度均值亮度、灰度标准差/相对对比度、HSV 饱和度；
- 动态：帧间灰度/结构变化率、结壳或火焰面积变化率、角点数量变化率/角点速度；
- 过程：由 Process State Agent 产生的状态摘要，在 `alignment_quality in {exact, interval, segment}` 时才进入视觉-过程 late fusion。

先用 synthetic tensor 验证 `mixture_weights.sum(-1)=1`、KL 非 NaN、重参数化梯度、mask、空先验和不确定性 finite，再使用真实火眼三类图片/视频窗口。论文中原有的 ROC-AUC、分类准确率和消融结果只属于论文数据，不能复制到本项目结果表。

```text
ROISequence [B,T,3,H,W]
  → spatial_encoder (ConvNeXt-Tiny/ViT)
  → temporal_encoder (Transformer/GRU/TCN)
  → z, mu, logvar, mixture_logits
  → conditional Gaussian mixture prior(feature guide)
  → KL alignment + fuzzy-label loss + optional contrastive loss
  → class head + uncertainty head + key-frame attention
```

最小损失形式应显式写在代码和实验配置中：

```text
L = L_cls
  + λ_kl · KL(q(z|x) || p(z|feature_guide))
  + λ_fuzzy · L_fuzzy_label
  + λ_temp · L_temporal_consistency
  + λ_contrast · L_contrastive (optional)
```

每个损失都要有开关和单元测试。专家先验只能来自已定义的静态/动态征兆和人工规则，不能用测试集标签生成输入特征。过程分支只有在 `alignment_quality` 达到配置门槛时启用；否则只训练视觉分支并把 `process_missing=["video_mapping"]` 或具体缺失字段列表传下去。

#### M5：多模态晚融合和不确定性

默认采用：

```text
visual_embedding + process_state_embedding(masked) + expert_prior
  → gated late fusion
  → class/risk/uncertainty heads
```

cross-attention、compact bilinear pooling 和图模型作为消融组，不作为第一版在线必需路径。已有 `CrossModel.py:10` 和 `CrossModelViews.py:9` 的 CrossAttention 只能作为工程参考；其 graph1/graph2 节点输入与火眼 ROI 不兼容，禁止直接把图模型接入视觉流程。

### 19.4 过程状态模型和视觉分支的边界

`Code/model/twoChannel/modelClass.py` 的 `mGraphDataset` 依赖 `graph1_node.csv/graph2_node.csv/edges/labels`、5类图标签和图节点结构，不能直接读 `v1` 的 `[5744,30,14]`，只能参考其训练/评测组织和图特征思想。Process State Agent 先使用 14 维窗口与现有 CNN/1DCNN/LSTM baseline，再抽出 `TemporalEncoder` 统一时序接口。

没有视频-过程样本级对应时：

- 过程模型单独训练和评测；
- 运行时没有过程窗口就输出 `process_missing=["process_snapshot"]`；
- JEV 可使用离线统计形成的策略先验，但不能把它写成当前视频的同步测量；
- 诊断报告标注 `alignment_quality=unknown`；
- 只有未来有槽号/时间窗映射时，才开启任务级 late fusion 并单独做有/无过程分支消融。

## 20. JEV/Laya 路由器：具体迁移方案

### 20.1 采用方式

### 21.1 RSI 的产品定义

RSI 在本项目中是受控离线演化系统：它从运行轨迹和人工反馈提出候选变更，经冻结评测、专家审核和版本发布后影响下一批任务。它不是在线自改权重，也不直接批准工艺结论。

### 21.2 RSIHub/FlashRSI 迁移到本地目录

```text
  evaluator.py        # frozen set canonical evaluator

  publisher.py        # human-approved active version
  cli.py              # inspect/evaluate/promote/reject
Code/agentic/tests/test_rsi_gate.py
```

参考 RSIHub 的七步流程：

```text

  → rollout on train split
  → analyze trajectory/feedback
  → mutate allowed files
  → validate mutable surface and novelty
  → canonical frozen evaluation
  → gate + human approval + record/publish
```

允许修改的 mutable surface：

```text

Code/agentic/rsi/candidates/knowledge_queries/**

```

禁止修改：冻结评测集、评测器、安全规则、模型权重、人工确认结果、生产控制配置。每个 candidate 保存 parent ID、diff、来源 run_id、提议模型、目标指标、风险说明和审批状态。

### 21.3 Reef 的评测和发布语义

参考 Reef `EvaluationResult`、`UpdateCandidate`、`SelectionDecision` 的分离：

- `Evaluator` 只测 candidate，不决定发布；
- `Gate/Selector` 根据指标和安全门槛决定 accept/reject；
- `Publisher` 只发布 approved candidate，并保留 current version；
- reject 不删除 candidate，进入 archive 供 RSI 分析。

本项目至少设三类 gate：

1. **质量 gate**：知识引用支持率、证据完整率、视觉/过程评测不能低于当前版本下限；
2. **安全 gate**：危险样本 simple 漏放率、无测量数值过热度拦截率、越权动作拦截率必须达标；
3. **效率 gate**：在质量和安全不恶化的前提下，才比较 P95 时延、Token 和人工耗时。

### 21.4 Reflexion critique memory

参考 Reflexion 的 `last_attempt`、`reflexion` 和持久化 memory，在本项目保存结构化 critique：

```json
{
  "run_id": "run-xxx",
  "agent_id": "diagnosis_aggregator",
  "failure_type": "missing_evidence|invalid_citation|route_misclassified|format_error",
  "observation": "复核指出……",
  "root_cause": "……",
  "candidate_fix": "……",
  "repeat_count": 2,
  "eligible_for_rsi": true
}
```

只把重复缺陷和有证据支持的改进送入 RSI；单次模型幻觉直接进入人工负例和评测集，不自动修改提示词。

### 21.5 DeepSeek SuperAgent 的 Ticket/Worker 语义

参考 `dsh-superagent-prototype` 的 Source→Thread→Eval→Ticket→Assignment→Executor：

| DeepSeek 概念 | 铝电解项目概念 | 具体实现 |
|---|---|---|
| Source/Trigger | 视频上传/图片上传/人工补拍事件 | `InspectionTask` + `TaskEvent` |
| Thread | 一个巡检任务的连续状态 | `thread_id` + checkpointer |
| Eval/Mandate | JEV 诊断准入和路由理由 | `JevRouteDecision` |
| Ticket | 一次可审计诊断任务 | `DiagnosisTicket` |
| Assignment | 分配到某个 Agent/profile | `AgentAssignment` |
| Executor/Worker | 视觉、RAG、案例、过程或聚合 Agent | LangGraph node/worker |
| Report/Attention | Agent 输出/人工待确认问题 | `AgentResult`/`HumanReviewRequest` |

每个 Ticket 要有 `ticket_id`、`stage`、`attempt`、`route`、`worker_id`、`health`、`retry_count`、`report_id`、`human_decision`。参考其 retry/backoff/health 语义，实现有限重试和可恢复任务，不复制 GitHub/Feishu source connector。

### 21.6 RSI 验收

固定一个已知缺陷，例如“知识引用格式错误”：

1. 运行记录产生 critique；
2. RSI 生成 prompt/规则候选 diff；
3. candidate 在 train split 上回放；
4. frozen evaluator 在 gate/sealed split 上评测；
5. 安全/质量 gate 判断；
6. 未经人工批准的 candidate 不会被在线加载；
7. 批准后可查看版本、指标、diff、来源和回滚入口。

## 22. LangGraph 企业级编排实现细节

### 22.1 状态与 reducer

将现有 `DiagnosisState` 拆成 typed state：任务、媒体、质量、视觉、过程、案例、知识、JEV、循环结果、诊断、复核、人工、审计。并行节点写入带 reducer 的 `evidence_bundle`，禁止多个节点无规则覆盖同一个 dict。

### 22.2 并行和重试

- full_loop 使用官方 `Send`/map-reduce 或受控 `asyncio.gather`；选择一种方式并封装，不在每个节点自行开线程。
- 本项目使用 LangGraph `Send` fan-out；worker 边界用 `config/worker_policies.json` 配置单 Agent 的 timeout、最大重试数、指数退避及可重试异常，并允许任务级受限覆盖。策略 ID、error code、attempt 和实际退避写入 AgentResult。
- 不要直接给 Send worker 节点叠加 LangGraph `RetryPolicy`：当前 worker 边界会把失败转换成结构化 `AgentResult(status="failed")`，LangGraph 节点因此正常结束，原生 RetryPolicy 无法观察内部失败且会产生重复策略。超时取消通过 `_cancel_event` 协作通知；同步阻塞 worker 无法被强行终止，需保留这一限制。
- 子 Agent 输出失败时保留 `AgentResult(status="failed")` 和 error code，聚合器根据证据覆盖决定升级或人工。
- 设最大协作轮次，例如 `max_full_loop_rounds=2`；达到上限直接进入 human。

### 22.3 真正的人工暂停恢复

目标代码形态：

```python
def human_review_node(state):
    decision = interrupt({
        "run_id": state["run_id"],
        "draft": state["diagnosis"],
        "evidence": state["evidence_bundle"],
        "issues": state["review"].get("issues", []),
        "allowed_actions": ["approve", "amend", "reject", "request_retake"],
    })
    return apply_human_decision(state, decision)

graph = builder.compile(checkpointer=checkpointer)
graph.invoke(input_state, config={"configurable": {"thread_id": thread_id}})
graph.invoke(Command(resume=decision), config={"configurable": {"thread_id": thread_id}})
```

本地先使用 `InMemorySaver`/SQLite checkpointer，生产形态再评估 Postgres。验收时必须模拟进程重启、重复 resume、非法 action 和并发审核。

### 22.4 运行事件和可观察性

使用 `stream_mode` 的 tasks/updates/custom 事件或统一 `TraceEvent`，每个事件至少有：`run_id`、`thread_id`、`ticket_id`、node、agent_id、stage、status、started_at、finished_at、elapsed_ms、model_profile、attempt、error_code、evidence_ids。

不保存模型私有思维链；保存可审计的输入摘要、结构化输出、证据引用、错误和人工动作。
